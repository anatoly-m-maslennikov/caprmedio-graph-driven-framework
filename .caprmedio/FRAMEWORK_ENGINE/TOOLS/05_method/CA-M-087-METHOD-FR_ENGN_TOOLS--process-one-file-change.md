# Process one project-path action

Use this flow for one Git-admitted project-path action. The subject can be one file or one non-empty folder. One folder action is one action, one Journal event set, and one commit; it is not expanded into one action per contained file.

1. A registered adapter establishes one logical repository-path action from its substrate event. `COMMIT_TRIGGER` observes the Git-admitted project frontier: tracked paths plus untracked paths not excluded by Git ignore rules. It excludes `.caprmedio_runtime` and every other top-level dot-directory except `.caprmedio`. It coalesces repeated observations with the same adapter and source-event identities into one stable trigger containing repository identity, subject kind, observed before-path and after-path candidates, observation time, and the structured LLM-session candidate resolved from explicit invocation context or the adapter's host interface, then hands that trigger unchanged to the `COMMIT_CHANGE_SET` end-to-end interface. Multiple paths changed under one unambiguous non-root folder in one callback form one folder trigger. The adapter does not classify Artifact meaning.
2. `COMMIT_CHANGE_SET` invokes the shared deterministic `COMMIT_CONTEXT` gathering logic. The same logic remains available through the standalone read-only Finder interface. Resolve one file or non-empty folder identity. Treat creation as `ADD` and disappearance as `REMOVE`. Otherwise derive `moved` from a path change and `updated` from the selected carrier state. Map `moved=false, updated=true` to `UPDATE`, `moved=true, updated=false` to `MOVE`, and `moved=true, updated=true` to `MOVE+UPDATE`; reject `false, false` as no change. For a folder, seal its complete ordered file-entry set and one aggregate digest; empty folders are outside the Git-backed frontier.
3. For a valid Atom file, decorate context with upstream typed relations resolved through the canonical relation-kind registry. For an ordinary file or folder, use an empty source set. Graph defects remain diagnostics and do not block an otherwise valid logger action.
4. Resolve the explicit author or default it to the current operator's full GitHub username. Validate the LLM application name and host session UUID through the registered application adapter, with an explicit validated value taking precedence, and fail closed rather than guess. Resolve one `occurred_at` and calendar date in the configured timestamp timezone. Seal structured `llm_session`, `occurred_at`, adapter and source-event provenance, subject kind, identity, action, paths, revisions, digests, Git base, ordered typed `sources`, singular resulting file or folder `result`, stable event and action identities, `previous_result_event` when one exists, and validation results as schema-version-3 `COMMIT_CONTEXT`. Atom versions remain author-declared; ordinary files and folders use logger-owned operational revisions. If a non-`ADD` subject has no accepted prior result event, seal a `recovered` baseline candidate only from sufficient governed evidence.
5. Run the complete flow in dry-run mode to return the sealed context, complete predicted Journal sidecar record set and partitions, repository lease availability, and Git message projected from the structured change event without mutation. Show `<app>:<uuid>:<occurred_at>` only as a derived presentation; do not write session provenance into an Atom or Projection.
6. Within the end-to-end apply, `COMMIT_CHANGE_SET` calls peer Doer `APPEND_CHANGE_RECORDS`. It acquires the repository-scoped apply lease, repeats every stale-context, frontier, identity, relation, version, recovery-evidence, index, and Git-base preflight, validates and uses the sealed author and event time without recomputation, appends and fsyncs the complete ordered idempotent sidecar record set, and returns its ordered receipt set with the live lease token. Its internal Journal and runtime-state writes do not emit another Hook trigger.
7. `COMMIT_CHANGE_SET` resumes its own commit boundary, validates the complete receipt set and live lease, repeats the mutation-boundary checks, stages exactly the one project-path subject action plus all and only its receipt-bound Journal lines, creates one commit from the deterministic message Projection, verifies the commit tree with rename detection disabled so the exact before-path and after-path boundary remains observable, verifies every related record, message, and parent Git base, and then releases the lease.
8. Return the common Tool result envelope with the Journal receipt set, lease disposition, and commit identifier on apply or their predicted values on dry-run. After a partial append or post-append commit failure, retain one observable blocked action and reuse the same event identities, `llm_session`, `occurred_at`, and existing receipts on retry rather than duplicate or redefine a record. A different action waits until the blocked action succeeds or an operator explicitly resolves it.
