# Summary

Deliver sealed lifecycle dispatch interface

## Scope

The Project-local MCP entrypoint contract. This specification defines the interface, not an executable Carrier.

## Claim

The entrypoint is one selected route under CA-D-527 and accepts no independent outer request/result. Its CA-D-527 `request.parameters` carries the typed lifecycle boundary: requested operation/result; exactly one complete new target Carrier set for Create, or exactly one complete current target/predecessor Carrier set for Update, Replace, or Change Status; and, for Replace, the complete accepted set of one or more distinct successor Carrier sets. It also carries the exact target/predecessor identity and locator, expected current Version/digest, proposed result or status mapping, and current qualified status model and model revision. Create and explicit Change Status accept any Status that resolved current Role/Type model admits, without a retained Draft-history or Journal admission/success prerequisite. `mode` remains preview unless the CA-D-527 outer request explicitly executes with its sealed operator authorization; an adapter envelope does not add authority.

The entrypoint returns CA-R-1828 only as the route-specific payload of CA-D-527's result. CA-D-527 remains the sole owner of outer disposition, started Run identities/definition bindings, actual terminal outcome, and independent Journal diagnostics when append is attempted. A Summary-changing Update returns a terminal non-effect `replace_handoff`; Replace is a separately admitted new outer request with fresh exact definitions, currentness, and permission, never inherited Update permission.

## Details

### Subject-only Update variant

The existing `update_atom` route's `request.parameters` additionally accepts exactly `{target, subject_patches, subject_intent_sha256, subject_profile?, semantic_assessment_report?}` for one Subject-only Update. `target` is exactly the existing complete descriptor with `atom_id`, `path`, `filename`, `version`, `digest`, `lifecycle`, `status`, `updated_at`, `content_role` and `type`, preserving actual absent-Type representation. It selects one complete eligible non-archived original, not a Draft, archive, delivered or projected copy; carried Status and placement remain exact preconditions. `subject_patches` is the closed ordered Subject-only list under CA-R-866, CA-D-425 and CA-D-623. Scalar `governs` replacement or replacement of one `depends_on` entry uses exactly `{field, old, new}`; the dependency's exact current `old` value must identify one existing entry. A `depends_on` entry addition or removal uses exactly `{field, operation: "add"|"remove", value}`; removal's exact current `value` must identify one existing entry. Complete `depends_on` set replacement uses exactly `{field, operation: "replace_set", old, new}`, with `old` equal to the exact current collection and `new` the complete explicit proposed collection. Unknown fields, caller-supplied indexes, missing or ambiguous current values, a wrong complete-set precondition and duplicate proposed dependencies fail; no implicit entry merge or duplicate acceptance is introduced. These are required input shapes, not an implementation or admission claim. Omission of `subject_profile` means `legacy`. `subject_intent_sha256` is CA-D-425's lowercase full intent hash.

This variant derives its complete intended proposal from the pinned source and explicit Subject spans; it accepts no complete `proposed` Carrier, `frontmatter`, `content`, caller class, successors, legacy identity proof/mapping, additional independent target, or other fields. `semantic_assessment_report` retains exactly CA-D-585's `{path, digest}`; it is required for an ordinary value-changing effect under CA-R-1892 and may be absent for pure preparation, truthful no-op, or an exact member of CA-R-866's instructed Subjects-only batch. Report/assessment identifies the intended proposal before effect-time metadata materialization. A replacement-required or unresolved result remains a non-effect handoff/refusal.

CA-D-425 defines the sealed intent and the subordinate exact-byte `predecessorArchive` effect. For a value change, the outer `target_frontier` is exactly the ordered current path then predecessor-history path; `effects` is exactly the ordered objects `{type: "subjectUpdate", path, atom_id, before_version, version, subject_intent_sha256}` for the current Carrier and `{type: "predecessorArchive", atom_id, version, path, sha256, lifecycle}` matching the sealed history intent. For no-op, the frontier contains only the current path and effects is empty. These descriptors request only that one target's current/history transition; no unrelated effects are admitted. CA-O-067/CA-O-145 and CA-O-129 reuse their existing one-target assessment and lifecycle bindings. At application require the exact CA-D-527 execute envelope, current source/definition/permission evidence, actual selected session, and actual in-memory CA-O-030 Action start, then repeat complete source/report/intent/destination validation. No caller Boolean or independent adapter envelope is an execution capability. Return actual materialization/current/history/effect facts inside CA-D-527's one result; independent Journal observation does not gate that result or authorize replay. Generic parameters and local standalone apply rejection remain intact; this is not bulk execution, a new route or local transport permission.

For the instructed Subjects-only batch, existing `update_atom` accepts exactly `request.parameters = {subject_batch: {path, digest}}`, with safe Project-relative packet path and lowercase SHA-256. The closed schema1 packet remains `{schema_version: 1, subject_profile: "approved", git_checkpoint, atoms}`, with ordered nonempty `atoms: [{target, subject_patches, draft?}]` using the existing target/patch descriptors. `draft`, when present, is exactly `{path, digest}` for actual full edit-draft bytes; all members have draft pins or none do. Reject malformed/unknown fields, duplicate targets, unsafe paths, wrong packet digest, mixed draft pins and out-of-packet effects. Packet order is effect order. The actual instruction and existing outer request Initiative/Operator authorization admit that exact packet; no additional form, review/pause response, content-review round, confirmation receipt or fabricated approval is required. Hashes/checkpoints alone are not authority.

The caller composes commit-current → bounded `stage_subject_batch` calls → commit-drafts → archive/promote → existing graph operation after successful batch completion; a separately instructed map-only batch stays admitted. `git_checkpoint` records the actual pre-batch commit as recovery evidence, not another gate. The public per-member current effect is exactly `{type: "subjectUpdate", path, atom_id, before_version, version}` and predecessor effect is exactly `{type: "predecessorArchive", atom_id, version, path, sha256, lifecycle: "archived"}`, derived from the exact packet, without an initial `subject_intent_sha256` requirement; derive fresh native intent internally when needed. For every draft-backed member, append its exact `draft.path` to that member's ordered target frontier after current and any required archive paths, and append exactly `{type: "draftRemoval", path: draft.path, atom_id: target.atom_id, sha256: draft.digest}` to its effects. This applies even when the canonical update is a truthful no-op: canonical Version/time/history stay unchanged while actual derived-draft consumption is reported separately. Existing ordinary singleton intent/assessment/frontier semantics remain unchanged.

Execute distinct independent one-target effects with real child Run lineage. Retain normal local target/draft/patch/layout, exact source-before, conditional-write, archive, Version/time and readback checks; do not add a separate full-candidate validation or review round. Restore canonical ID/original Status from a pinned draft and use actual time; a full proposal cannot broaden Subjects-only authorization. Stop first failure/uncertainty, keep completed effects and held/remaining sources untouched, preserve native failed-write handling, and never automatically roll back/replay/retry/resume the batch. Actual effects and logging failures are separate observations. After verified canonical output and any required predecessor readback, conditionally remove only that member's exact packet-pinned draft bytes. If draft cleanup fails or its bytes have drifted, stop and report the actual cleanup failure, preserving the published canonical Revision and archive; do not roll them back or remove another file. Any draft cleanup remains bound to its exact packet path/hash. No new executor, Tool family, report type or public caller authorization Boolean is introduced.

For an authorized Archive, the model-admitted status transition proceeds even when it newly breaks Relations.
