# What governs non-delivery placement at the Project root?

what permitted root-placement boundary reconciles the delivery-only rule with the explicitly required legal, authority, runtime, **and** temporary Carriers?

## Evidence

CA-D-327 admits **only** delivery Directory Carriers at the Project root. CA-D-337 requires root `LICENSE` **and** `LICENSES/`; CA-D-318 requires the Project authority root; CA-D-320 **and** CA-D-321 require separate runtime **and** disposable-state roots. these obligations cannot **all** satisfy a literal delivery-only restriction. CA-D-445's native Scope Unit folder bindings do **not** by themselves admit a standalone license file **or** every administrative repository file.

## Principle check

CA-M-002 rejects a second placement registry, CA-M-006 requires the explicit Carrier rules **to** agree, **and** CA-R-1490 protects legal evidence **and** retained operational history. these Principles reject deleting the legal **or** runtime Carriers merely **to** satisfy the blanket rule. they do **not** establish a complete generic exception domain **or** authorize an arbitrary new root layout.

## Disposition

preserve the existing sources **and** Carriers pending a precise root-placement policy. either retire the obsolete blanket restriction with demonstrated coverage **or** replace it with a rule that reuses the authoritative specific bindings. do **not** silently exempt every root file, duplicate the concrete bindings, move legal information into authority, **or** classify administrative folders as Structural Entities. changing the restrictive Summary requires a new Atom identity under CA-R-1432.
