## Summary

Define CFEL

## Claim

### Formal Claim

```CFEL
# model
p{::occurrence}:: [value format]{::value count};

p.*[name format]{::immediate name count};

p.**[name format]{::recursive name count};

p.*[name format]{::immediate name count}:: [value format]{::value count}
```

### Prose Claim

CFEL (CAPRMEDIO Formal Expression Language) is the formal notation for
Subject addresses and fenced Formal Claims. CFEL is a model component beside
Graph and Carrier: Graph contains Nodes and Relations; CFEL addresses and
constrains them. CFEL syntax neither creates a Node, Relation, Property,
Carrier fact, Workflow step, nor evaluator result.

An `IF` membership condition can bind an unbound variable to each matching member of its declared selection; a variable already bound in the surrounding scope is tested against membership without rebinding. A parenthesized multi-line `THEN` body uses the same binding in each complete expression. `FOR EACH` states universal quantification under its own Declaration and does not revoke the IF binding rule.

In a Formal Claim, `# model` and `# instances` are ordering comments for the model and instance expressions that follow; they do not assert graph facts. A `$variable` explicitly binds an anonymous selected Entity or instance; repeated occurrences in its scope select the same identity. A bare Model kind identifies its model entity. `<Kind>` refers to that declared Model kind as a Format; `$x[<Kind>, (conditions)]` binds an existing instance of that kind subject to grouped conditions. `$<Kind>` selects anonymously. Repeated anonymous selections have the same domain but assert neither identical nor different referents; a named participant expresses the same selected identity. Model-entity selection remains explicit, including IF membership over `(Node, Node.**)`; an instance selector does not turn a model entity into a data-layer fact. `$relation[<Relation>, (.Name = IS_PROPERTY_OF)]` selects a Relation descriptor; it does not assert a data-graph fact. A `FOR EACH` body uses its own declared participant and scope; the active Subject identifies the Claim focus and supplies no implicit participant. For a selected instance population, `$<Journal>{::1}` or `$journal[<Journal>]{::1}` each count selected logical Journal instances within the Current Project. `$x.p{::n}` counts occurrences of Property p on the selected bearer; `p{::occ} :: [<Kind>]{::valuecount}` separately bounds Property occurrences and direct values. Relation bounds remain in their before/after-operator slots and count links per written endpoint.

CFEL uses these graph-address forms:

- `X//Y` selects a narrower Primary Node; `$x[<X>, (.Name = Name)]` selects an
  existing named instance of a declared kind, including a Property instance borne by its data bearer.
- `X.p` addresses Property p borne by X. A Subject selection may appear in an address or inside a filtered Node
  expression in a Formal Claim: `X//(.p := V)` combines an admitted Property
  value with selection of X. `:=` belongs to this Subject-selection syntax; it
  is not a free-standing Formal-Claim value assignment.
- `Whole/Part` expresses one immediate containment fact. `X >| Axis` and `Axis |< X` are opposite written views
  of one classification fact. A bare qualified address references its declared entity or instance. No `@` reference operator is required; `@N` identity/version tags retain their separate meaning.
- Parentheses group one expression. `;` separates complete expressions;
  a line break has no conjunction or disjunction meaning.

Text values use double quotes when needed to distinguish literal text from CFEL syntax; otherwise an unambiguous value may remain bare, including a multiword value such as `Scope Contract`. For example, `"A/B"` is text containing a slash. A name or path used as a reference retains its declared identity; a text value does not become a model reference. Within double-quoted text, `\"` represents a literal double quote and `\\` represents a literal backslash. Reject every other escape and any incomplete trailing backslash; JSON escape rules are not imported. This applies to values in Formal Claims and Subject selectors.

In Formal Claims, `X := Y` expresses an allowed literal value and `X :: C` expresses a value constraint. All applicable HAS_ALLOWED_VALUE alternatives, including inherited alternatives, combine by OR; all applicable HAS_VALUE_CONSTRAINT restrictions, including inherited restrictions, combine by AND. Final admissibility is `(HAV := #1 OR #2 OR ...) AND (HVC :: #1 AND #2 AND ...)`. If no HAS_ALLOWED_VALUE group exists, omit that group (true): there is no enumeration restriction. For example, `x := a; x := b` can be written `x := a | b`; `x :: [string]; x :: {::1}` can be written `x :: [string]{::1}`. These Relations do not assign a value to an occurrence. `=` and `!=` test conditions,
and `==` states a required or derived conclusion. `in` and `not in` are the
admitted membership tests. Numeric comparison and addition use the separately
defined `>`, `>=`, `<`, `<=` and `+`; they are distinct from Relation
operators. Property occurrence, direct-value, immediate-name
and recursive-name counts are distinct:

`{::n}`, `{::n+}` and `{::n..m}` state allowed cardinality bounds on their
qualified selection; `{=n}` tests a count condition, `{>n}` tests whether the
actual count is greater than n using the existing numeric `>`, and `{==n}`
concludes a required or derived count. These test/conclusion forms are not
allowed bounds. A Relation has independent outgoing and
reverse cardinalities: `Source {::forward}((RELATION)){::reverse} Target`.
A named Property has at most one occurrence per corresponding bearer; its applicable value constraints determine whether it is required. A present Property has a value, including nonempty child structure for a structural parent. `p:: {::0..1}` specifies a direct-value count with its applicable inherited format. Other omitted annotations are unspecified, not zero. `[format]` applies to direct
values; a name selector is not a value selector. A `p.**` count aggregates
selected distinct descendant Property identities below p within each selected
bearer, independently of direct values and other bearers.

The named constructs `IF`/`THEN`, `UNIQUE`, `DETERMINES`, `COUNT`, `MAX`,
and `FENCED_LABELS` are admitted with the semantics in their own CFEL Rules.
`LOOKUP(R, q)` and `?==` are admitted CFEL forms with semantics in their own
CFEL Rules; the `?==` ordered-default Rule supplies its chain semantics.
Boolean `AND` and `OR` combine conditions; parenthesize mixed AND/OR
expressions to state their grouping explicitly. `>>` is delivery notation with the
semantics of the delivery Rule; `!(selectors)` excludes branches from a
delivery selection. `$x[<Kind>]` binds an existing selected instance and `$x.p`
reads its Property. A CFEL syntax form is not a binary Node Relation. A Requirement/Declaration describes
a canonical or derived Relation direction; it does not authorize a second
stored inverse fact.

Each CFEL Rule defines the meaning of its notation literal or bounded construct.
The literal is syntax, not an executed CFEL expression, value assignment, state
creation, or a new model entity.

A direct Relation Declaration owns shared meaning and endpoints. A derived inverse Declaration retains the reverse HAS_INVERSE binding and its own alias, when present. A qualified or other non-inverse derived view retains its source, endpoint transformation and qualification; derivation alone does not imply unconditional endpoint reversal. `alias($boundRelation) == "token"` binds an already-bound exact Relation name to lexical notation. `$direct[<Relation>, (.Name = DIRECT)] <--> $derived[<Relation>, (.Name = DERIVED)]` binds distinct inverse Relations in the direct Declaration. It never equates their identities. These metadata forms do not create literal-to-Node graph links.

A graph Relation connects its declared endpoint domains, including declared model entities or instances and, where a value Relation declares them, literal values or value constraints. A literal remains a value, not a model entity. A CFEL syntax literal is not a
graph Relation or model entity, and its glyph or literal operand does not create
another model entity. Each direct Relation Declaration supplies shared meaning and a
formal Host/Target signature with typed selectors whose universe is known, or
with declared variables bound to that universe. Within a Relation Declaration
Formal Claim only, `$host ((RELATION)) $target` is the reusable generic
signature: its untyped variables range over that declared entity-or-instance
universe and exclude literals. It declares neither a Relation fact nor instance
data. Known endpoint kinds remain typed selectors. This generic Relation signature binding applies within Relation Declarations; typed bindings can also select model entities where their universe is declared.

Concrete directional alternatives describe the same canonical Relation fact:
`Step ((IS_CONTAINED_BY)) Workflow` and
`Workflow <((IS_CONTAINED_BY)) Step`. The bare forward form
`Step ((IS_CONTAINED_BY)) Workflow` remains valid. In reverse writing,
normalization swaps canonical Source/Target and the two written endpoint count
slots. This syntax does not grant an inverse Relation permission. The Relation Declaration states the Host, Target and applicable counterpart direction. `HAS_INVERSE` applies to inverse Relations; a qualified non-inverse derived view retains its source, transformation and qualification.

In RMED Claims, all formal content is a fenced block labelled `CFEL`. CFEL
body syntax and Markdown-fence-label parsing are separate concerns. This Definition
describes the admitted language contract; it does not claim a complete parser
or evaluator. An unimplemented construct remains an adoption and conformance
gap, not evidence that the construct has different semantics.

A Model kind can supply an object Format, but a Format, Bool value, or other literal does not become an instance merely by its Format or notation. Instance selection requires its declared source binding. No value-format-to-instance rewrite is implied by the CFEL overview.

`$relation[<Relation>, (.Name = IS_DECLARED_BY)]` is the qualified derived view of a GOVERNS fact whose source is a Requirement/Form Declaration; it reverses that selected fact while retaining the qualification. It is not a general inverse of GOVERNS or a permission for every Relation.
