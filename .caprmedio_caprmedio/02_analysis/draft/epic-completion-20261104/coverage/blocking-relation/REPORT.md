# Plan blocking Relation pair — source proposal

Current CA-R-1580@27 defines `BLOCKS` as Direct from a prerequisite Plan to the dependent Plan. The latest human decision reverses the authored direction: `IS_BLOCKED_BY` is Direct from the dependent Plan to its prerequisite, and `BLOCKS` is its Derived inverse. The current endpoint domain remains Plan instances; the prerequisite must be Done before the dependent may start.

The packet proposes one same-ID revision of CA-R-1580 as the derived `BLOCKS` Declaration and one unallocated Draft for direct `IS_BLOCKED_BY`. Each has the correct Relation-object address, typed Plan endpoints, inverse binding, derivation classification and short Semantics. Neither Relation signature contains counts or an alias. CA-R-1580's metadata, ID and Summary are preserved; the exact Current predecessor and 16 supporting Current sources are pinned in `manifest.json`.

The effective Plan instance whitelist must separately admit the required outgoing `IS_BLOCKED_BY` and `BLOCKS` directions. Relation-object endpoint signatures and inverse binding do not supply those permissions. CA-R-2511 currently contains no such named permissions, while the Node instance default is zero. Determine their supported cardinalities from governing rules or a human decision; this packet does not invent them.

**Adoption requires coordinated migration.** CA-D-471 currently requires authoring `relations.blocks` on the prerequisite Plan, and CA-M-306 tells authors to express start dependencies using `BLOCKS`. Those Current directions conflict with the new direct/derived decision. Review their source contracts, existing data, readers and tests before changing how direct facts are represented; no new serialization field is proposed here. CA-E-504, CA-E-404, CA-E-622, CA-M-239 and CA-R-1592 consume the logical BLOCKS view and require review without silently rewriting historical facts.
