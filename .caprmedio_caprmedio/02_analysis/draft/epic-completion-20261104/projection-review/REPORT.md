# Independent review: Projection identity packet

Review is against the staged packet and its pinned frontier, not an adoption decision. `evidence.json` records the packet-manifest digest, 23 authority/candidate pin comparisons, and seven staged Projection frontmatters; all 23 compared hashes matched when checked. No Current source or packet was modified.

## Actionable findings

1. **Form admission is not carried explicitly by the ten new Claims.** Each value preview claims `Projection/(.Form: X)`, a bearer qualification; Current CA-R-2538 explicitly uses `Projection.Form: X;` to admit each of Catalog, Map and Hub. The revised CA-R-2538 removes those expressions and none of the new ten supplies an equivalent explicit property-value admission. This risks losing existing allowed-value authority and leaving new Forms unadmitted. Minimum correction: assign the allowed-value admission `Projection.Form: X;` once to its own value Declaration, focus its active Subject on that property/value according to the approved Subject convention, and retain no duplicate enumeration on CA-R-2538. Confirm against the governing syntax before promotion.

2. **Seven existing Projection identities need a concrete migration.** CA-PROJ-020 through CA-PROJ-026 currently all serialize `form: Map` and have no `scope_unit` field. If they share the same resolved Scope Unit, these 7 IDs contradict the new `(Form, Scope Unit) → ID` dependency. Missing references mean their actual Scope Units cannot be deduced from these files. The new seven distinct proposed Form labels can distinguish the views, but the packet is a plan: explicitly bind each old ID to its new Form and its exact Scope Unit identity, validate all seven references and cross-check ID collisions before adopting. Preserve IDs only if the authorized migration explicitly permits that transition; the prospective rule alone does not establish that migrated instances already conform.

3. **Root Project identity requires an actual reference binding.** The new `Projection.Scope Unit` reference is exactly one `[Scope Unit//]` value, consistent in shape with the Current `Projection.Source.Named Selection` reference declaration. CA-R-2524 also declares that Project is the root Scope Unit and has no Scope Unit ID. Consequently a migration or reader must resolve the Project as a Scope Unit target by its declared identity, without assuming a Scope Unit ID, name or Carrier path. CA-R-2562 compares reference target identities through supplied bindings and fails unresolved references; neither preview nor staged instances prove such a Project-root binding or serialization exists. Specify and test the actual stable binding without inventing an identifier or modifying source structure.

## Checks and boundaries

- The two proposed `DETERMINES` clauses correctly express both `(Form, Scope Unit) → ID` and `ID → (Form, Scope Unit)` over selected Projection states; Named Selection is absent from both keys. Their evaluator operates in one explicit Project context under CA-R-2562, so global cross-Project uniqueness must not be inferred from them.
- `Projection.ID`, `Projection.Form`, and the new `Projection.Scope Unit` each declare one property and one value. The new reference uses the established reference-format pattern; Project-root resolution remains the distinct gap above. The parent Form declaration no longer duplicates an allowed-value enumeration, subject to finding 1.
- The ten proposed value names are unique: Catalog, Map, Hub and seven distinct views. Proposing seven names does not establish their Current admission or map their existing instances. The packet contains no Terms Graph Form and does not modify the Terms Graph sources; existing optional Terms Graph authority must not be treated as retired merely because its new Form is deferred.
- Each Form candidate's active Subject is currently a selected Projection, while its Claim is also a selected Projection; whether that expresses value-admission focus is the defect in finding 1. The unallocated Scope Unit Declaration's active Subject is the dependent Property, and the ID rule focuses Projection.ID.
- `Source.Named Selection` remains a source description, not an identity component. CA-D-635's proposed filename may contain it, but filename and source-selection changes must not allocate another Projection ID under the decision.
- The 56 held legacy expressions were not mapped. No runtime, parser, migrated instance, source promotion, rebuild, or release is established by this review.

## Acceptance checks

Recheck all packet and authority hashes immediately before use; resolve finding 1 with value-focused declarations and validate each exactly once; allocate IDs through the designated owner; prove the two dependencies with repeated states, renamed selections, changed source versions, different Forms and different Scope Units; validate a Project-root reference with no Scope Unit ID as well as a non-root reference; perform a collision-checked seven-ID mapping with provenance and explicit history treatment; rebuild and validate all seven views and their actual readers. Keep Terms Graph and the held expressions separately governed.
