# Project Settings carrier reconciliation

Ten pinned prospective previews reconcile the merged Project.Settings owner with the existing physical carrier partitions. The `manifest.json` pins each live source and preview, plus the current model and carrier authority used. No Current file was edited. All Summaries and source identities remain unchanged; no fresh ID or retirement is proposed for these ten. CA-E-459 contains the explicit `CA-R-ALLOCATE` reference placeholder for the separately proposed CA-R-1750 successor and must not be applied before allocation.

- CA-D-358 keeps `caprmedio_framework_settings` as the physical carrier identifier, governed under Carrier/File rather than inventing Project.Settings.Identifier. CA-D-359 retains the existing Project-specific `000_CAPRMEDIO_framework/caprmedio_framework_settings.toml` location and one authoritative carrier for its registered partition. CA-D-360 preserves exact path, revision, digest, actual-observation and Journal receipt protections; the merged model does not reset history.
- CA-D-361 and CA-D-366 keep their existing carrier-specific field specifications and closed schema. Their obsolete categorical bans on initialization inputs versus instance choices are removed; this does not open CA-D-366's TOML signature or authorize adding an unregistered key. Physical partition placement, duplicate selected values and any migration still require the applicable field and carrier rules; no automatic file move is proposed.
- CA-E-458 and CA-E-459 evaluate their respective physical partitions, preserve Project isolation, per-file schema and provenance checks, and avoid claiming the entire logical Project.Settings has exactly one physical carrier. CA-E-459's check against an independent unauthorized Name or Prefix source remains. Its successor-rule reference is a placeholder.
- CA-D-370 keeps the exact required control-root destination and prohibition against choosing another authority root when an explicit locator is encoded. CA-D-371 requires encoding the declared selected locator values when explicitly selected. Neither turns an optional MODEL value into an unconditional authored field. R1980@16 permits zero or one direct value; R1978@15 permits an optional property occurrence with one or more string values when present. The previews add no fallback or claim that an operation is ready when it lacks an independently required effective locator; consumer readiness and fallback remain governed elsewhere.
- CA-D-377 retains the ban on Atom metadata and the existing revision-binding rule for the physical Framework Settings Carrier.

The explicit-user logical merge establishes one conceptual owner; it does not itself specify how two pre-existing field-bearing files resolve conflicts or migrate data. This packet does not implement a loader, move files, mutate values, update a Journal, validate closed schemas against live carriers, or settle settings subjects handled by other lanes. Integration must combine overlapping per-source previews and replace the placeholder, then recheck live hashes and run appropriate validation.
